# Screen Design: Complete Status Capability

**Route**: existing `/build`

**Reference**: canvas 1d Status mode; desktop peer mode is a spec-driven extension
**Purpose**: present the complete package status, current headline results, requirements and exact
actions for one build/condition revision.

## Information order

1. Status heading and workspace build identity.
2. Viewing conditions: load, SYS/ENG/WEP pip draft/total, hardpoints, Apply and Reset.
3. Independent structural validity and completeness facts.
4. Ordered package issue list or explicit none-reported statement.
5. Power draw and capacity.
6. Six headline cards: shield, armour, sustained DPS, selected jump, top speed, unladen mass.
7. Qualification summary or explicit none-reported statement.
8. Assembly requirements: retail fields, conditional Merc Coin and materials.

Controls precede the values they affect. Structural evidence precedes results. Requirements follow
the headline set, matching the durable reference hierarchy.

## Desktop

Add Status as a peer in the central capability selector shown by canvas 1c. The rail action selects
it without routing. The central outlet uses fluid cards and full-width issue/assembly
regions. The persistent rail remains a compact mirror of the same revision and contains no issue
records.

## Tablet

- Landscape: the complete capability uses the main outlet; a compact slot ledger may remain only
  when both regions meet content/touch requirements. No separate rail.
- Portrait: shared header and wrapping capability navigation precede a full-width Status document.
  Conditions stack or wrap; headline cards use at most two columns when labels/units/states fit.

## Mobile and 400% zoom

Use the canvas 1d in-workspace Status concept, but capability navigation wraps or uses a shared
overflow-safe primitive with 44 CSS-pixel targets. Status becomes one stacked document region. The
mock's duplicate quick-stat dock and slot ledger are suppressed while Status is active. A slot action
switches to the exact slot surface; leaving that surface can return to Status.

Mobile landscape may use two headline columns only when measured content remains complete. Portrait
and 400% zoom default to one. Long diagnostics, exact identities, units and RTL translations wrap.

## Result anatomy

Every owner projection renders:

- localized meaning;
- locale-formatted value plus visible unit, or owner-provided semantic state text;
- only relevant selected/native conditions;
- all owner qualifications without feature 003 reclassification;
- one named detail action to its owning capability.

Sustained DPS always remains the package firing value. When the selected power condition is
retracted, the card identifies DPS as firing/deployed-native output rather than fabricating a
retracted number or unavailable state.

## Issues

Structural facts use a definition list. Issues use one ordered semantic list item per package entry
with visible code/severity, diagnostic helper/fallback text, structured context and optional exact
slot action.

## Lifecycle states

- no active build: existing workspace empty state;
- pending current context without stale figures;
- ready with all validity/completeness combinations;
- issue target present/absent;
- no issues/no qualifications;
- owner exact-zero, lower-bound, incomplete, unavailable, infinite and Merc Coin absent states;
- invalid pip draft with previous settled results retained;
- application projection failure distinct from package unavailable.

## Announcements and accessibility

Visible content is not live. One hidden polite region announces settled issue/qualification count
changes; initial/unchanged/stale states are silent. The workspace retains one visible `h1`, logical
subheadings and named semantic regions. Controls work by touch/pointer, motion respects reduced
motion, and any conformance statement names all constitutional keyboard exclusions.
